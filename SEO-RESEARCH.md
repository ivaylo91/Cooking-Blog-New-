# How this recipe blog should do SEO

Research and audit notes, 4 November 2026.

## Summary

- The groundwork is already solid. Every indexable page sets its own canonical, the site is server-rendered with `lang="bg"`, search results are `noindex, follow` and not blocked in robots.txt, the sitemap lists recipes with their photos, and the Recipe markup carries every property Google requires plus most of the recommended ones. Commit `2eefbed` ("SEO: correct canonicals, search-friendly titles, richer sitemap and schema") did most of this work.
- **The favicon may not show in Google.** The site's only icon is `src/app/icon.svg`. Google's supported favicon formats are "BMP, GIF, ICO, PNG, JPEG, PPM, and TIFF", and SVG is not on the list ([Google](https://developers.google.com/search/docs/appearance/favicon-in-search)). On a phone, the favicon and site name sit at the top of every result.
- **Large image previews are not allowed yet.** Discover's large images are "Enabled by the `max-image-preview:large` setting" ([Google](https://developers.google.com/search/docs/appearance/google-discover)), and the site does not set it. For a food blog read on phones, this is a one-line change.
- **Open Graph tags are partly wrong on some pages.** Next.js merges metadata shallowly. A page that sets `openGraph` replaces the layout's whole object, and a page that sets none inherits it unchanged ([Next.js docs](node_modules/next/dist/docs/01-app/03-api-reference/04-functions/generate-metadata.md), "Merging"). As a result, `/za-ivo` shares with the home page's `og:url` and title, and recipe pages lose `og:site_name` and `og:locale`.
- **Some missing recipes may return 200, not 404.** The recipe route has a `loading.tsx`, so the response starts streaming before `notFound()` runs. Next.js then keeps the `200` and adds `noindex` ([Next.js docs](node_modules/next/dist/docs/01-app/02-guides/streaming.md), "Status codes"). Renaming a slug in the admin leaves the old URL dead with no redirect.
- **Recipe markup gaps:** one image ratio, steps without `name` or `url`, `PT0M` durations, and an empty `keywords` string on recipes with no tags.
- **For content, the gap is depth, not quality.** Google's raters reward documented first-hand experience in recipes ([Search Quality Rater Guidelines](https://static.googleusercontent.com/media/guidelines.raterhub.com/en//searchqualityevaluatorguidelines.pdf)). The byline already claims it. A short "Бележки на Иво" section after the method would show it.

## Brief

Find what Google, schema.org, web.dev and the bundled Next.js 16 docs say a single-author Bulgarian recipe blog should do for search, and check the code against it. Readers are Bulgarian speakers, mostly arriving from Google on phones. Recommendations respect the owner's decisions in [DESIGN.md](DESIGN.md) and [PRODUCT.md](PRODUCT.md), such as no preamble before the recipe and the welcoming home heading. Sources are the organisations that own the guidance. Anything not checked at its source is listed under "Not verified". Production could not be reached from this machine, so every finding comes from the code and the docs, not from live responses.

## 1. Technical SEO

### Crawling, indexing and status codes

- **robots.txt controls crawling, not indexing.** robots.txt is "not a mechanism for keeping a web page out of Google". Use `noindex` instead ([Google](https://developers.google.com/search/docs/crawling-indexing/robots/intro)). If a page is disallowed, "any information about indexing or serving rules will not be found" ([Google](https://developers.google.com/search/docs/crawling-indexing/robots-meta-tag)). The site disallows only `/admin` (`src/app/robots.ts:7`) and keeps `/tarsene` crawlable with `robots: { index: false, follow: true }` (`src/app/tarsene/page.tsx:16`). That is correct.
- **A 200 response does not guarantee indexing.** "An HTTP `2xx (success)` status code doesn't guarantee indexing." When the content is "an empty page or an error message", Search Console reports a soft 404 ([Google](https://developers.google.com/search/docs/crawling-indexing/http-network-errors)).
- **Streaming fixes the status code early.** Next.js says that once a Suspense fallback such as `loading.tsx` renders, "the server must commit to `200 OK`". A later `notFound()` then gets an injected `noindex` instead of a 404. To get a real 404, call `notFound()` before any Suspense boundary, or check the slug in Proxy ([streaming.md](node_modules/next/dist/docs/01-app/02-guides/streaming.md), [loading.md](node_modules/next/dist/docs/01-app/03-api-reference/03-file-conventions/loading.md), "Status codes"). Both `src/app/recepti/loading.tsx` and `src/app/recepti/[slug]/loading.tsx` exist. A URL outside `generateStaticParams`, such as a deleted or renamed recipe, can therefore return 200 with `noindex` instead of 404. Google removes it either way. The real cost is that old links never return a 404 or a redirect.
- **Moved pages need permanent redirects.** Google asks for "server side permanent redirects from the old URLs to the new URLs", kept for at least a year ([Google](https://developers.google.com/search/docs/crawling-indexing/site-move-with-url-changes)). Next.js `redirects` with `permanent: true` return 308 ([redirects.md](node_modules/next/dist/docs/01-app/03-api-reference/05-config/01-next-config-js/redirects.md)). A `redirect()` mid-stream "becomes a client-side redirect rather than an HTTP redirect header" ([streaming.md](node_modules/next/dist/docs/01-app/02-guides/streaming.md)). The admin form generates slugs (`src/components/admin/RecipeForm.tsx:11`), and `updateRecipe` writes any new slug (`src/app/admin/actions.ts:145`), with no redirect from the old one.
- **Metadata streaming is safe for Google.** Since 15.2, `generateMetadata` output can be streamed into `<body>`. Next.js says this is "interpreted correctly by bots that execute JavaScript", such as Googlebot. HTML-limited bots, such as social preview crawlers, still get it in `<head>` ([generate-metadata.md](node_modules/next/dist/docs/01-app/03-api-reference/04-functions/generate-metadata.md), "Streaming metadata"). No change is needed.

### Canonicals, hosts and URLs

- **How Google picks a canonical.** Redirects and `rel="canonical"` are both "a strong signal", and sitemap inclusion is a "weak signal". Pick one host (www or apex) and redirect the others to it. Google does "not recommend using noindex to prevent selection of a canonical page" ([Google](https://developers.google.com/search/docs/crawling-indexing/consolidate-duplicate-urls)). Canonicals here resolve against `metadataBase` (`src/app/layout.tsx:30`), so they are absolute. They are only as good as `NEXT_PUBLIC_SITE_URL`, which falls back to `http://localhost:3000` when unset (`layout.tsx:10`, and five other files).
- **Trailing slashes are already handled.** By default Next.js "will redirect URLs with trailing slashes to their counterpart without" ([trailingSlash.md](node_modules/next/dist/docs/01-app/03-api-reference/05-config/01-next-config-js/trailingSlash.md)).
- **Transliterated slugs are endorsed.** Google advises "readable words rather than long ID numbers" and hyphens rather than underscores. For other scripts it mentions using "transliterated words" ([Google](https://developers.google.com/search/docs/crawling-indexing/url-structure)). Slugs such as `/recepti/gyuvecheta` fit this.
- **Paginated and filtered lists.** Google says to give each page in a sequence its own canonical, not page 1's. It no longer uses `rel="next"`/`"prev"`. For filter variants, it suggests `noindex` or a robots.txt pattern ([Google](https://developers.google.com/search/docs/specialty/ecommerce/pagination-and-incremental-page-loading)). The shelves already use self-canonical pages (`src/app/recepti/page.tsx:42-47`). Time and difficulty filters canonicalise to their shelf. That is a reasonable hint, and Google may ignore it because the filtered list differs.
- **`lang` is for people, not Google.** Google says "We don't use any code-level language information such as `lang` attributes". It detects language from visible content ([Google](https://developers.google.com/search/docs/specialty/international/managing-multi-regional-sites)). `lang="bg"` (`layout.tsx:74`) still matters for screen readers and hyphenation. hreflang applies only when there are several language versions, so it is not needed here.

### Sitemap

- **What Google reads.** Google uses `<lastmod>` "if it's consistently and verifiably accurate", "ignores `<priority>` and `<changefreq>`", and wants "fully-qualified, absolute URLs" ([Google](https://developers.google.com/search/docs/crawling-indexing/sitemaps/build-sitemap)). Image entries may sit on another domain. Google calls that "fine, as long as you verify both domains in Search Console" ([Google](https://developers.google.com/search/docs/crawling-indexing/sitemaps/image-sitemaps)).
- **Next.js support.** The Next.js `images` field writes these entries ([sitemap.md](node_modules/next/dist/docs/01-app/03-api-reference/03-file-conventions/01-metadata/sitemap.md)).
- **What the site emits.** Recipes use their own `updated_at` (`src/app/sitemap.ts:31`). Shelves and static pages share the newest recipe's date (`sitemap.ts:15,26`), which is not that shelf's last change. Recipe photos are on `*.supabase.co`, a domain the owner cannot verify in Search Console.
- **IndexNow.** It is supported by Bing, Yandex, Seznam, Naver, Yep and Amazon. Google is not listed ([IndexNow FAQ](https://www.indexnow.org/faq)). For a Bulgarian Google audience it is optional.

## 2. On-page

- **Titles.** Google wants titles that are "descriptive and concise", without "repeated or boilerplate text", and with the site name at one end after "a hyphen, colon, or pipe". There is no length limit, but titles are truncated "to fit the device width". Google also draws title links from `<h1>`, `og:title` and `WebSite` structured data ([Google](https://developers.google.com/search/docs/appearance/title-link)). The pattern "`<рецепта>`: домашна рецепта | Кулинарният блог на Иво" (`src/app/recepti/[slug]/page.tsx:82`, `layout.tsx:33`) follows this. The brand suffix is long and will often be cut on phones, which is acceptable because the dish name comes first.
- **Meta descriptions.** They should be unique and accurate, can include facts, and may be generated "programmatically" if they stay readable ([Google](https://developers.google.com/search/docs/appearance/snippet)). The recipe description plus "Готово за N мин, M порции." (`[slug]/page.tsx:76-79`) is a good template.
- **Image alt text and file names.** Write alt text that is "useful, information-rich", and "Avoid filling alt attributes with keywords". Use "filenames that are short, but descriptive". Use real `<img>` elements, because CSS backgrounds are not indexed ([Google](https://developers.google.com/search/docs/appearance/google-images)). The hero has `alt={recipe.title}` (`[slug]/page.tsx:238`). Card images use `alt=""` (`src/components/RecipeCard.tsx:87,121`), which is right for accessibility because the title is in the same link. Step photos read "Стъпка N" (`src/components/RecipeSteps.tsx:91`), which says nothing about the photo. Upload names are random UUIDs (`src/components/admin/ImageUpload.tsx:50`).
- **Discover.** Discover wants images "At least 1200 px wide" with `max-image-preview:large`, and warns against generic images such as a logo in `og:image` ([Google](https://developers.google.com/search/docs/appearance/google-discover)). The robots meta rule `large` allows "A larger image preview, up to the width of the viewport". Without the rule, Google uses "the default size" ([Google](https://developers.google.com/search/docs/crawling-indexing/robots-meta-tag)). Next.js writes it from `robots: { 'max-image-preview': 'large' }` ([generate-metadata.md](node_modules/next/dist/docs/01-app/03-api-reference/04-functions/generate-metadata.md), `robots`).
- **Open Graph merging.** In Next.js, "All `openGraph` fields from `app/layout.js` are **replaced**" when a page sets `openGraph`. A page that sets none inherits them ([generate-metadata.md](node_modules/next/dist/docs/01-app/03-api-reference/04-functions/generate-metadata.md), "Merging"). The layout's `openGraph` includes `url: siteUrl` and `title: siteName` (`layout.tsx:41-48`). `/za-ivo` sets no `openGraph` (`src/app/za-ivo/page.tsx:15-20`), so it advertises the home page's URL and title. Recipe and shelf pages set their own, so they drop `siteName`, `locale` and the recipe `url`. Neither `opengraph-image.tsx` exports `alt`, which Next.js turns into `og:image:alt` ([opengraph-image.md](node_modules/next/dist/docs/01-app/03-api-reference/03-file-conventions/01-metadata/opengraph-image.md)).
- **Site name.** WebSite markup "must be on the home page", needs `name` and `url`, and may list `alternateName` values in order of preference. Google also reads `og:site_name`, `<title>` and headings ([Google](https://developers.google.com/search/docs/appearance/site-names)). The site emits WebSite markup from the layout on every page (`layout.tsx:56-69,87`). That is harmless, but only the home page counts.
- **Sitelinks search box.** Google removed it "starting on November 21, 2024". There is "no need" to remove the markup, and it "won't cause issues" ([Google blog](https://developers.google.com/search/blog/2024/10/sitelinks-search-box)). The `SearchAction` in `layout.tsx:64-68` is now inert.
- **Favicon.** The favicon must be square, "at least 8x8px", with "larger than 48x48px" recommended. It must be crawlable by Googlebot-Image and on a stable URL, in one of "BMP, GIF, ICO, PNG, JPEG, PPM, and TIFF" ([Google](https://developers.google.com/search/docs/appearance/favicon-in-search)). Next.js accepts `icon.png` or `favicon.ico` in `app/` next to `icon.svg` ([app-icons.md](node_modules/next/dist/docs/01-app/03-api-reference/03-file-conventions/01-metadata/app-icons.md)).
- **Breadcrumbs.** Google recommends trails that show "a typical user path". The feature is listed as "available on desktop" ([Google](https://developers.google.com/search/docs/appearance/structured-data/breadcrumb)), so it matters little for a phone audience. LAYOUT-RESEARCH.md already argued against a visible trail. Keeping the JSON-LD (`[slug]/page.tsx:178-201`) costs nothing.

## 3. Structured data

General rules: "Don't mark up content that is not visible", markup "must be a true representation of the page content", and items "missing required properties are not eligible for rich results". "All image URLs specified in structured data must be crawlable and indexable" ([Google](https://developers.google.com/search/docs/appearance/structured-data/sd-policies)).

### Recipe

Google requires `image` and `name`. It recommends `aggregateRating`, `author`, `cookTime`, `datePublished`, `description`, `keywords`, `nutrition.calories`, `prepTime`, `recipeCategory`, `recipeCuisine`, `recipeIngredient`, `recipeInstructions`, `recipeYield`, `totalTime` and `video` ([Google](https://developers.google.com/search/docs/appearance/structured-data/recipe)). schema.org types `recipeYield` as QuantitativeValue or Text, and the times as ISO 8601 durations ([schema.org/Recipe](https://schema.org/Recipe)). The table compares Google's guidance with what the site emits.

| Property | Google's guidance | What the site emits (`src/app/recepti/[slug]/page.tsx`) |
| --- | --- | --- |
| `name` | Required | Title (line 130). ✔ |
| `image` | Required. Several high-resolution images in "16x9, 4x3, and 1x1", each "50K pixels" or more | One original URL (132), on supabase.co. Omitted when there is no photo, so a recipe without a photo is not eligible. |
| `author` | Person, `name` holding "only the name", `url` to a page that "uniquely identifies the author" ([Article](https://developers.google.com/search/docs/appearance/structured-data/article)) | Person "Иво" with `/za-ivo` (133). ✔ |
| `datePublished` / `dateModified` | Include a timezone ([Article](https://developers.google.com/search/docs/appearance/structured-data/article)) | Supabase `timestamptz` values, which carry an offset (134-135). ✔ |
| `prepTime` / `cookTime` / `totalTime` | ISO 8601. Use `prepTime` "in combination with cookTime" | Always emitted, so a no-cook salad says `cookTime: PT0M`, and a recipe with no times says `totalTime: PT0M` (136-138). |
| `recipeYield` | Servings "with just a number". Required if nutrition is per serving | "4 порции" (139). Valid text. A bare number is the stated preference. |
| `recipeCategory` / `recipeCuisine` | Text | Category name. Cuisine defaults to "Българска" (`supabase/schema.sql:62`). ✔ |
| `keywords` | Comma-separated. Don't repeat the category or cuisine | Tag names (142). Empty string when there are no tags. |
| `recipeIngredient` | Text per ingredient | Amount, unit, item, note (143-145). ✔ |
| `recipeInstructions` | HowToStep with `text` ("only instructional text"), and recommended `name`, `url` ("directly links to the step") and `image` | `text` and `image` only (146-150). Step `<li>` elements have no `id` (`RecipeSteps.tsx:49`). |
| `aggregateRating` | Needs `ratingValue` and `ratingCount`. Users "should be able to see that aggregate rating on the page" ([Review snippet](https://developers.google.com/search/docs/appearance/structured-data/review-snippet)) | Only when `rating_count > 0` (154-163). Visible as "4.5 от 5 · N оценки" (`RatingStars.tsx:106`). ✔ |
| `nutrition.calories`, `video` | Recommended | Absent. There is no data for either, and none should be invented. |

**Self-serving reviews.** Google's self-serving review rule covers `LocalBusiness` and `Organization` ([Google](https://developers.google.com/search/docs/appearance/structured-data/review-snippet)), not Recipe. Visitor ratings, one per IP (`src/app/recepti/actions.ts:74`), are allowed. Ivo must never rate his own recipes or seed counts.

### Person, ProfilePage, WebSite, BreadcrumbList

- **ProfilePage.** It needs `mainEntity` with a `name`. Recommended properties include `image`, `sameAs`, `description`, `dateCreated` and `dateModified`. The page's "primary focus... must be a single person" affiliated with the site ([Google](https://developers.google.com/search/docs/appearance/structured-data/profile-page)). `/za-ivo` qualifies and emits `name`, `url`, `image` and `description` (`za-ivo/page.tsx:47-59`). `sameAs` is worth adding only if Ivo has public profiles.
- **WebSite** and **BreadcrumbList** were covered under on-page above. HowToStep's `name`, `url` and `image` come from Thing, and `text` comes from CreativeWork ([schema.org/HowToStep](https://schema.org/HowToStep)).

## 4. Content and E-E-A-T

- **Google's own questions.** Google asks: "Does your content clearly demonstrate first-hand expertise", and "Do pages carry a byline, where one might be expected?" It says "trust is most important" among the E-E-A-T qualities. It warns against "changing the date of pages to make them seem fresh". It has no preferred word count ([Google](https://developers.google.com/search/docs/fundamentals/creating-helpful-content)).
- **What raters look for.** The rater guidelines (11 September 2025) define Experience as "first-hand or life experience for the topic" (section 3.4). They say "Trust is the most important member of the E-E-A-T family". On recipe pages, "the recipe itself and important supporting content" should be "near the top". The "Highest: Recipe" example earns its rating because the author "documented her extensive experimentation". "Low: Recipe 1" lacks "user reviews or comments" ([Search Quality Rater Guidelines](https://static.googleusercontent.com/media/guidelines.raterhub.com/en//searchqualityevaluatorguidelines.pdf)).
- **What the site already does.** The recipe comes first with no preamble. The byline reads "Иво, сготвено и снимано в моята кухня", with a portrait linking to `/za-ivo` and published and updated dates in `<time>` (`[slug]/page.tsx:274-299`). The update date appears only when the Sofia calendar day changes, so trivial edits do not pose as updates (`[slug]/page.tsx:55-57,291`). Ratings and comments follow the method. `/za-ivo` states how the recipes are made, in claims the owner has confirmed.
- **What is missing.** The recipe pages show no evidence of experience beyond the byline line. Tips, substitutions, what went wrong the first time, or how the dish keeps would provide that evidence. Placed after the method, this respects the no-preamble decision and matches the raters' "supporting content". Shelf pages are grids with no text of their own. One or two sentences per category in Ivo's voice would help readers and give the page unique content. Neither change needs filler, and the rater guidelines penalise filler.

## 5. Performance (Core Web Vitals)

- **Thresholds and weight.** "Core Web Vitals are used by our ranking systems", but Google "always seeks to show the most relevant content, even if the page experience is sub-par" ([Google](https://developers.google.com/search/docs/appearance/page-experience)). The thresholds, at the 75th percentile, are LCP ≤ 2.5 s, INP ≤ 200 ms and CLS ≤ 0.1 ([web.dev](https://web.dev/articles/vitals)).
- **Mobile-first parity.** Google indexes the mobile version, so mobile needs the same content, structured data, metadata and alt text. Don't "lazy-load primary content upon user interaction" ([Google](https://developers.google.com/search/docs/crawling-indexing/mobile/mobile-sites-mobile-first-indexing)). The site serves one responsive HTML document, and ingredients and steps are both in the DOM, so this is satisfied.
- **From the code.** The recipe hero uses `preload` (`[slug]/page.tsx:245`). Fonts come from `next/font`. Pages are cached with `"use cache"` and prerendered through `generateStaticParams`. Speed Insights collects field data (`layout.tsx:101`). The one open item, three `fetchPriority="high"` cards on `/recepti`, is already LAYOUT-RESEARCH.md item 9. The Speed Insights field data, not this note, should drive further work.

## 6. Audit

### Already done well

- Per-page absolute canonicals, with no inherited "/" (`layout.tsx:36-40`, `page.tsx:17`, `recepti/page.tsx:47`, `[slug]/page.tsx:84`, `za-ivo/page.tsx:19`).
- Self-canonical pagination and a 404 past the last page (`recepti/page.tsx:42-47,82-85`).
- Search is `noindex, follow` and stays crawlable (`tarsene/page.tsx:16`, `robots.ts:7`).
- Search-friendly titles and fact-bearing descriptions (`[slug]/page.tsx:76-82`, `recepti/page.tsx:51-59`).
- Recipe markup: all required properties when a photo exists, most recommended ones, and an honest `aggregateRating` (`[slug]/page.tsx:123-176`). JSON-LD is escaped against `</script>` (`JsonLd.tsx:6`).
- Image sitemap entries and per-recipe `lastModified` (`sitemap.ts:29-34`).
- A per-recipe 1200×630 share image that carries the dish photo (`[slug]/opengraph-image.tsx`).
- Byline, dates and an About page with ProfilePage markup (`[slug]/page.tsx:274-299`, `za-ivo/page.tsx:47-59`).
- `lang="bg"`, `og:locale` `bg_BG` and readable transliterated slugs.

### Fixes

**High**

1. **Add a raster favicon.** SVG is not among Google's supported favicon formats ([Google](https://developers.google.com/search/docs/appearance/favicon-in-search)). Export the existing mark as a square PNG of at least 96 px (a multiple of 48 is safe) and add it as `src/app/icon.png`, or add `src/app/favicon.ico`. Keep `icon.svg` for browsers. Next.js emits a `<link>` for each ([app-icons.md](node_modules/next/dist/docs/01-app/03-api-reference/03-file-conventions/01-metadata/app-icons.md)). File: `src/app/`.

2. **Allow large image previews.** Add `robots: { index: true, follow: true, "max-image-preview": "large" }` to the root `metadata` ([Discover](https://developers.google.com/search/docs/appearance/google-discover), [robots meta](https://developers.google.com/search/docs/crawling-indexing/robots-meta-tag)). `tarsene` and the missing-recipe branch set their own `robots`, which replaces this one under shallow merging, so they stay `noindex`. File: `src/app/layout.tsx`.

3. **Fix Open Graph merging.** Move the shared fields (`siteName`, `locale`, `type`) into one exported constant and spread it into every page's `openGraph`. Give each page its own `url`, for example `url: \`/recepti/${recipe.slug}\``. Give `/za-ivo` its own `openGraph` and `twitter` titles ([generate-metadata.md](node_modules/next/dist/docs/01-app/03-api-reference/04-functions/generate-metadata.md), "Overwriting fields"). Drop `url: siteUrl` from the layout, so a page that forgets to set one emits no URL rather than the home page's. Files: `layout.tsx`, `page.tsx`, `recepti/page.tsx`, `recepti/[slug]/page.tsx`, `za-ivo/page.tsx`.

**Medium**

4. **Keep old recipe URLs working.** Either lock the slug once a recipe is published (simplest), or record old slugs and 308-redirect them in Proxy, before rendering ([Google](https://developers.google.com/search/docs/crawling-indexing/site-move-with-url-changes), [streaming.md](node_modules/next/dist/docs/01-app/02-guides/streaming.md)). Files: `src/components/admin/RecipeForm.tsx`, `src/app/admin/actions.ts`, and for redirects a table in `supabase/` plus `src/proxy.ts` (widen the `matcher`).

5. **Return a real 404 for unknown recipes.** Call `notFound()` before any Suspense boundary. One way is to move the recipe skeleton from `loading.tsx` into a `<Suspense>` inside the page, after a cached existence check, following the pattern in [streaming.md](node_modules/next/dist/docs/01-app/02-guides/streaming.md). Confirm with `next build` that Cache Components accepts the structure, then check the status with `curl -I`. Files: `src/app/recepti/[slug]/page.tsx`, `src/app/recepti/[slug]/loading.tsx`.

6. **Complete the recipe steps and images.** Give each step `<li>` an `id` such as `stapka-1`. Add `url: \`${recipeUrl}#stapka-${n}\`` to each `HowToStep`. Supply 16:9, 4:3 and 1:1 image URLs ([Google](https://developers.google.com/search/docs/appearance/structured-data/recipe)). Generate the crops at upload, or point at `/_next/image` URLs on the site's own domain. That also takes the images off `supabase.co`, which the owner cannot verify in Search Console for image sitemaps ([Google](https://developers.google.com/search/docs/crawling-indexing/sitemaps/image-sitemaps)). Files: `RecipeSteps.tsx`, `[slug]/page.tsx`, `sitemap.ts`, `ImageUpload.tsx`. This overlaps LAYOUT-RESEARCH.md item 8.

7. **Fail the build without a site URL.** Throw when `NEXT_PUBLIC_SITE_URL` is missing in production, and read it from one module instead of six `?? "http://localhost:3000"` fallbacks. A wrong value would move every canonical and sitemap entry to localhost ([Google](https://developers.google.com/search/docs/crawling-indexing/consolidate-duplicate-urls)). Files: a new `src/lib/site.ts`, then `layout.tsx`, `sitemap.ts`, `robots.ts`, `rss.xml/route.ts`, `[slug]/page.tsx`, `za-ivo/page.tsx`.

8. **Add Ivo's notes after the method.** Add an optional per-recipe "Бележки на Иво" text: tips, substitutions, storage. Show it below the steps, never above them ([helpful content](https://developers.google.com/search/docs/fundamentals/creating-helpful-content), [rater guidelines](https://static.googleusercontent.com/media/guidelines.raterhub.com/en//searchqualityevaluatorguidelines.pdf)). Files: `supabase/schema.sql`, `src/types/recipe.ts`, `RecipeForm.tsx`, `[slug]/page.tsx`. The content is the owner's to write, so the field stays empty until he does.

**Low**

9. **Tidy the Recipe JSON-LD values.** Omit `prepTime`/`cookTime` when either is 0, and keep `totalTime`. Omit `totalTime` when it is 0. Omit `keywords` when it would be empty. Optionally emit `recipeYield` as `[String(servings), \`${servings} порции\`]` ([Google](https://developers.google.com/search/docs/appearance/structured-data/recipe)). File: `[slug]/page.tsx:136-142`.

10. **Describe step photos.** Use alt text such as the first clause of the step text, not "Стъпка N". Name uploads `<slug>-<uuid>.<ext>` ([Google](https://developers.google.com/search/docs/appearance/google-images)). Files: `RecipeSteps.tsx:91`, `ImageUpload.tsx:50`.

11. **Make each shelf's `lastmod` its own.** Use the newest `updated_at` within each category, and the newest overall for `/` and `/recepti` ([Google](https://developers.google.com/search/docs/crawling-indexing/sitemaps/build-sitemap)). File: `sitemap.ts:15-27`.

12. **Move WebSite markup to the home page.** Add an `alternateName`, such as a Latin spelling, and drop the inert `SearchAction` ([site names](https://developers.google.com/search/docs/appearance/site-names), [Google blog](https://developers.google.com/search/blog/2024/10/sitelinks-search-box)). Files: `layout.tsx:56-69,87` and `page.tsx`.

13. **Add `og:image:alt`.** Export `alt` from both share-image routes, such as the recipe title or the blog name ([opengraph-image.md](node_modules/next/dist/docs/01-app/03-api-reference/03-file-conventions/01-metadata/opengraph-image.md)). Files: `src/app/opengraph-image.tsx`, `src/app/recepti/[slug]/opengraph-image.tsx`.

14. **Optional: noindex filtered views.** Mark time and difficulty views `noindex, follow` instead of relying only on the canonical ([Google](https://developers.google.com/search/docs/specialty/ecommerce/pagination-and-incremental-page-loading)). Unknown `?category=` values render an empty 200 page, and `notFound()` would suit them. File: `recepti/page.tsx`.

15. **Optional: a short introduction per shelf, in Ivo's words.** File: `src/lib/categories.ts` or a new column. This is the owner's call. DESIGN.md does not cover shelf copy.

Not recommended: a visible breadcrumb trail (see LAYOUT-RESEARCH.md), invented nutrition or video, and IndexNow ahead of the fixes above.

## Not verified

- **Live behaviour.** Production (`www.cookingblogofivo.com`) could not be reached from this network: HTTPS timed out and HTTP went to an ISP filter. The Vercel API did not return the project's domains. These are unchecked: the www/apex redirect, the 404 status of a missing recipe (item 5 rests on the Next.js docs, not a test), the rendered `<head>` on `/za-ivo` (item 3 rests on the documented merge rule), and whether Next.js inherits the root `opengraph-image` on pages that set `openGraph` without images.
- **Supabase robots.txt.** Whether `*.supabase.co` storage allows Googlebot-Image was not checked.
- **Bing Webmaster Guidelines.** The page renders client-side and could not be read, so no Bing claim is made beyond the IndexNow FAQ.
- **Rater guidelines page numbers.** Quotes come from the text of the 11 September 2025 PDF. Only section 3.4 is cited by number.
- **Favicon size.** Google's page states only "larger than 48x48px". The often-repeated "multiple of 48px" rule is not on the current page, so item 1 treats it as a safe choice, not a requirement.
